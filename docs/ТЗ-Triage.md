## 2. Назначение и цель создания системы

### 2.1. Описание вида деятельности, для которой создается система

Система создается для поддержки деятельности по тестированию программного обеспечения, а именно — для формирования оптимального порядка выполнения тестовых сценариев при подготовке тестового набора (регрессионного тестирования).

Тесты хранятся и сопровождаются во внешней системе управления тестами SmartBear Zephyr Scale. Эта система не содержит встроенного средства приоритизации тестов в рамках одного тестового набора, поэтому порядок выполнения тестов формируется тестовым инженером вручную. Система Triage автоматизирует ранжирование тестов на основе их метаданных и исторических данных о выполнении, формируя рекомендуемый порядок их запуска.

### 2.2. Требуемые значения показателей

Целевые показатели, которые должны быть достигнуты при внедрении системы (зафиксированы в материалах проекта):

- сокращение времени на формирование набора регрессионных тестов — на 23%;
- увеличение количества дефектов, обнаруживаемых при выполнении первых 25% тестов от сформированного набора, — на 7%.

Дополнительно, по результатам опроса целевой аудитории, ожидается сокращение времени, затрачиваемого на формирование тестового набора, не менее чем на 20%.

Достижение указанных показателей является критерием качества разработки.

## 3. Связанные характеристики

### 3.1. Краткие сведения об объекте

Объектом автоматизации является процесс приоритизации (формирования порядка выполнения) тестовых сценариев в отделе тестирования программного обеспечения ООО «Теком».

Тестовые сценарии и история их выполнения ведутся в системе управления тестами Zephyr Scale. В проекте используются два набора данных, сопоставленные с проектами Zephyr Scale: B2C (ключ проекта `SQM`) и B2B (ключ проекта `SB2B`). Для каждого теста доступны метаданные (приоритет, статус, метки, папка) и записи о его выполнениях (результат, время выполнения).

### 3.2. Условия эксплуатации и характеристики окружающей среды, каналы использования

Система представляет собой серверное веб-приложение, запускаемое локально. Каналы использования и условия эксплуатации:

- доступ пользователя осуществляется через веб-браузер (для отладки использовался Google Chrome); приложение по умолчанию доступно по адресу `http://localhost:8080`;
- для работы функций приоритизации требуется доступ к внешнему API Zephyr Scale (`https://api.zephyrscale.smartbear.com/v2`);
- для работы с большой языковой моделью требуется локально запущенный сервис Ollama (по умолчанию `http://localhost:11434`) с установленной моделью (модель по умолчанию — `qwen2.5:3b`);
- хранение результатов и артефактов выполняется в локальной файловой системе.

## 4. Требования к системе в целом

### 4.1. Требования к структуре и функционированию системы

Система реализуется как монолитное клиент-серверное веб-приложение с отрисовкой страниц на стороне сервера (server-side rendering). В составе системы выделяются следующие функциональные подсистемы:

- подсистема веб-интерфейса (серверный рендеринг страниц на Thymeleaf, статические ресурсы — CSS и клиентский JavaScript);
- подсистема интеграции с Zephyr Scale (получение тест-кейсов, выполнений, папок, статусов, приоритетов; создание тестовых циклов и выполнений);
- подсистема интеграции с большой языковой моделью через Ollama (получение списка моделей, загрузка модели, выполнение запросов в формате JSON);
- подсистема приоритизации (асинхронный конвейер вычисления весов атрибутов и AI-сортировки тестов, управление заданиями);
- подсистема хранения результатов (предлагаемые тестовые циклы и артефакты выполнения в файловой системе).

Информационный обмен между подсистемами выполняется через внутренние вызовы Java-компонентов, а с внешними системами — по протоколу HTTP (REST). Взаимодействие клиентской части с сервером выполняется по HTTP: запросом страниц и набором REST-эндпоинтов под префиксом `/api/`.

Режимы функционирования: интерактивный режим (работа пользователя через веб-интерфейс) и асинхронный режим выполнения заданий приоритизации (задание запускается, выполняется в фоне, его статус опрашивается клиентом; задание может быть отменено).

Степень централизации: данные о тестах централизованы во внешней системе Zephyr Scale; результаты работы системы централизованно хранятся в локальной файловой системе сервера приложения.

### 4.2. Требования к персоналу

Пользователями системы являются руководители отделов тестирования и аналитики ООО «Теком». Численность пользователей соответствует штату отдела тестирования. Пользователи должны обладать как минимум начальными знаниями и навыками в области тестирования программного обеспечения и уметь работать с системой управления тестами Zephyr Scale. Специальная подготовка для работы с веб-интерфейсом не требуется.

Для развертывания и сопровождения системы требуется специалист, владеющий запуском Java-приложений и настройкой сервиса Ollama.

### 4.3. Показатели назначения

Система должна сохранять работоспособность при изменении состава тестов и их метаданных в Zephyr Scale, а также при смене большой языковой модели. Состав используемой модели и шаблонов промптов является настраиваемым во время эксплуатации (выбор активной модели, загрузка новой модели, редактирование и версионирование шаблонов промптов, изменение размера контекста). Это обеспечивает приспособляемость системы к изменению процессов и параметров без изменения исходного кода.

### 4.4. Требования к надежности, безопасности, эргономике, эксплуатации и обслуживанию

- Надежность: при недоступности внешних систем (Zephyr Scale, Ollama) система должна сообщать пользователю понятное сообщение об ошибке и не прерывать работу остальных функций. Задание приоритизации должно корректно завершаться при отмене с очисткой созданных артефактов.
- Безопасность информации: секретные данные (токен Zephyr Scale, учетные данные Jira) не должны храниться в системе контроля версий. Они задаются через переменные окружения (`ZEPHYR_API_TOKEN`, `JIRA_*`) либо через локальный файл `secrets.yaml`, который не попадает в репозиторий и автоматически импортируется приложением.
- Эргономика: веб-интерфейс должен поддерживать темную, светлую и системную темы оформления, а также локализацию интерфейса (русский и английский языки). Для повышения восприятия информации используются иконки и индикаторы состояния элементов.
- Эксплуатация и обслуживание: запуск приложения выполняется средствами сборки Gradle; конфигурация задается в файле `application.yaml` и локальных переопределениях.

### 4.5. Требования к защите информации, патентной чистоте, стандартизации и унификации

Защита информации обеспечивается исключением секретов из репозитория (см. п. 4.4) и локальной обработкой данных тестов: использование локальной большой языковой модели через Ollama позволяет не передавать данные тестов на сторонние серверы.

Унификация обеспечивается единым стеком технологий: язык Java, фреймворк Spring Boot, шаблонизатор Thymeleaf, единый формат хранения результатов (JSON) и единое соглашение об именовании файлов шаблонов промптов и предлагаемых тестовых циклов.

## 5. Требования к функциям системы

### 5.1. Перечень задач, решаемых системой

Система должна обеспечивать выполнение следующих функций:

1. Просмотр списка тестовых сценариев из Zephyr Scale с фильтрацией (по проекту, приоритету, папке, статусу), сортировкой и постраничным выводом.
2. Выбор набора тестовых сценариев (не менее двух) и запуск приоритизации в асинхронном режиме.
3. Приоритизация в два этапа:
   - вычисление весовых коэффициентов значимости атрибутов для каждого теста средствами большой языковой модели;
   - сквозная AI-сортировка выбранных тестов с присвоением каждому тесту итогового коэффициента ранжирования.
4. Формирование предлагаемого тестового цикла (рекомендуемого порядка выполнения тестов) и его сохранение.
5. Просмотр и при необходимости ручная пересортировка предлагаемого тестового цикла, переименование цикла, выгрузка результата в формате JSON.
6. Отправка сформированного цикла в Zephyr Scale (создание тестового цикла и тестовых выполнений).
7. Управление большой языковой моделью: получение списка доступных моделей Ollama, выбор активной модели, загрузка модели, изменение размера контекста.
8. Управление шаблонами промптов (просмотр, сохранение новой версии, выбор активной версии) для двух типов промптов: вычисление весов (`weights`) и AI-сортировка (`aisort`).
9. Настройка темы оформления и языка интерфейса.

### 5.2. Требования к качеству реализации функций и форме представления выходной информации

Выходной информацией системы является предлагаемый тестовый цикл, сохраняемый в виде JSON-файла в каталоге `suggested_test_cycles/`. Для каждого теста в составе цикла фиксируются: ключ и наименование теста, набор весовых коэффициентов по восьми атрибутам, вычисленные детерминированные метрики и итоговый коэффициент AI-сортировки, по которому тесты упорядочиваются по убыванию.

Восемь атрибутов, для которых вычисляются веса: приоритет, статус, метки, количество выполнений, количество провалов, доля проваленных выполнений, статус последнего выполнения, время выполнения. Сумма весов нормируется к единице; коэффициенты AI-сортировки также нормируются.

Промежуточные артефакты каждого запуска (отправленные в модель промпты и полученные ответы) сохраняются в каталоге `llm/io/` в виде Markdown-файлов, что обеспечивает прослеживаемость результата.

Примечание о точности результата ранжирования. В материалах проекта в качестве методики оценки точности предусмотрены коэффициент ранговой согласованности Kendall τ (ожидаемое значение больше 0 при диапазоне значений от −1 до 1) и доля сохраненного относительного порядка LCS (ожидаемое значение больше 50%). На текущем этапе данные метрики зафиксированы как методика оценки и в исходном коде системы не реализованы.

### 5.3. Перечень и критерии отказов

К отказам системы относятся:

- недоступность внешнего API Zephyr Scale или ошибка авторизации при обращении к нему;
- недоступность сервиса Ollama или отсутствие выбранной модели;
- запуск приоритизации при выборе менее двух тестовых сценариев;
- ошибка разбора ответа большой языковой модели (некорректный или невалидный JSON, выход значений за допустимые границы).

При возникновении перечисленных ситуаций система должна сообщать пользователю об ошибке и не приводить к потере уже сохраненных результатов.

## 6. Требования к видам обеспечения

### 6.1. Математическое обеспечение

В основе ранжирования лежит модель взвешивания атрибутов теста. Для каждого теста большая языковая модель формирует весовые коэффициенты по восьми атрибутам (см. п. 5.2), которые проходят валидацию (нахождение значений в диапазоне от 0 до 1) и нормировку (приведение суммы к единице). На основе метаданных и истории выполнений детерминированно вычисляются метрики: число выполнений, число провалов, доля проваленных выполнений, статус последнего выполнения, суммарное время выполнения. Итоговый порядок задается коэффициентом AI-сортировки, формируемым моделью по совокупности тестов.

Методика оценки точности ранжирования (Kendall τ, LCS) описана в п. 5.2; в коде системы на текущем этапе не реализована.

### 6.2. Информационное обеспечение

Система не использует систему управления базами данных. Хранение данных организовано на основе файловой системы:

- предлагаемые тестовые циклы — JSON-файлы в каталоге `suggested_test_cycles/` (имя файла соответствует ключу цикла вида `{ключ проекта}-SR{номер}`);
- артефакты запусков приоритизации — Markdown-файлы в каталоге `llm/io/`;
- шаблоны промптов — версионируемые файлы в каталоге `llm/prompt_templates/` (соглашение об именовании `{модель}_ctx{размер контекста}_{weights|aisort}-{версия}.md`);
- настройки времени выполнения (активная модель, активные версии шаблонов, размер контекста) — файл `llm/llm-settings.json`.

Обмен данными с внешними системами выполняется по HTTP в формате JSON: с Zephyr Scale — через DTO-объекты (тест-кейсы, выполнения, папки, статусы, приоритеты, тестовые циклы и др.), с Ollama — через объекты запросов и ответов чата, списка моделей и загрузки модели.

### 6.3. Лингвистическое обеспечение

Язык программирования серверной части — Java (версия 21). Шаблоны страниц реализованы на Thymeleaf, клиентская логика — на JavaScript, стили — на CSS. Язык взаимодействия пользователя с системой — русский и английский (переключаемая локализация интерфейса).

### 6.4. Программное обеспечение

Серверная часть построена на фреймворке Spring Boot (версия 4.0.6) с использованием стартеров Spring MVC, Thymeleaf и JSON; сборка выполняется средствами Gradle. Приложение является кроссплатформенным за счет исполнения на виртуальной машине Java.

Внешнее программное обеспечение, необходимое для эксплуатации: сервис Ollama для запуска локальной большой языковой модели; доступ к системе управления тестами Zephyr Scale.

### 6.5. Техническое, метрологическое, организационное и методическое обеспечение

Специальные требования к техническому, метрологическому, организационному и методическому обеспечению не предъявляются. Для эксплуатации достаточно рабочей станции, удовлетворяющей требованиям к запуску среды исполнения Java и сервиса Ollama.

## 7. Состав и содержание работ по созданию системы

### 7.1. Перечень стадий и этапов работ

Разработка велась по инкрементной модели жизненного цикла. Выделяются следующие этапы:

1. Создание каркаса и базовой функциональности приложения на Spring Boot.
2. Реализация интеграции с Zephyr Scale (получение метаданных тестов и результатов их выполнения).
3. Реализация интеграции с большой языковой моделью через Ollama (установление связи и выполнение запросов).
4. Доработка веб-интерфейса для взаимодействия с моделью и для управления приоритизацией.
5. Реализация серверного конвейера приоритизации и формирования предлагаемых тестовых циклов.
6. Внесение улучшений (локализация, темная тема, настройки, повышение удобства интерфейса).

### 7.2. Сроки исполнения

Сроки исполнения работ соответствуют срокам выполнения выпускной квалификационной работы (см. п. 1.4).

### 7.3. Состав организаций-исполнителей

Работы выполняются одним исполнителем — разработчиком, указанным в п. 1.2.

Экспертиза технической документации проводится в порядке, предусмотренном для выпускных квалификационных работ.

## 8. Порядок контроля и приемки системы

### 8.1. Виды, состав, объем и методы испытаний

Контроль качества программного кода обеспечивается автоматизированными тестами, расположенными в каталоге `src/test/java/com/qligent/triage/`. Набор включает модульные тесты компонентов (приоритизация, валидация весов, работа с шаблонами промптов, клиенты Zephyr и Ollama, хранилище предлагаемых циклов), тесты веб-контроллеров, тесты сериализации и тест на корректность завершения асинхронного задания. Тесты выполняются средствами JUnit Platform через сборку Gradle.

Функциональная проверка системы выполняется через веб-интерфейс по сценарию: просмотр тестов в Zephyr Scale, выбор набора, запуск приоритизации, проверка сформированного предлагаемого цикла, отправка цикла в Zephyr Scale.

### 8.2. Общие требования к приемке работ по стадиям

Приемка работ выполняется по завершении этапов в соответствии с инкрементной моделью (см. п. 7.1). Критериями приемки являются работоспособность реализованных функций и прохождение автоматизированных тестов, а также соответствие целевым показателям, указанным в п. 2.2.

### 8.3. Статус приемной комиссии

Приемка результатов осуществляется в порядке защиты выпускной квалификационной работы.

## 9. Требования к подготовке объекта к вводу системы в действие

### 9.1. Преобразование входной информации к машиночитаемому виду

Преобразование входной информации не требуется: данные о тестах и их выполнениях получаются из Zephyr Scale в машиночитаемом виде (JSON) через API.

### 9.2. Изменения в объекте

Внедрение системы не требует изменений в самой системе управления тестами Zephyr Scale. Требуется предоставить системе токен доступа к API Zephyr Scale и (при использовании интеграции с Jira) соответствующие учетные данные.

### 9.3. Сроки и порядок комплектования и обучения персонала

Перед началом эксплуатации необходимо:

- настроить доступ к API Zephyr Scale (задать токен через переменную окружения или файл `secrets.yaml`);
- установить и запустить сервис Ollama и загрузить используемую модель;
- запустить приложение средствами сборки Gradle и открыть веб-интерфейс в браузере.

Специальное длительное обучение персонала не требуется; достаточно ознакомления с порядком работы через веб-интерфейс.

## 10. Требования к документированию

### 10.1. Перечень подлежащих разработке документов

- настоящее техническое задание;
- пояснительная записка к выпускной квалификационной работе;
- краткая инструкция по запуску приложения.

### 10.2. Перечень документов на машинных носителях

Документация ведется в электронном виде в формате Markdown в каталоге `docs/`. Исходный код, конфигурация и автоматизированные тесты хранятся в репозитории системы контроля версий.

## 11. Источники разработки

Техническое задание и система разрабатываются на основании внутренних материалов проекта (задание на выпускную квалификационную работу, пояснительная записка) и официальной документации используемых инструментов: системы управления тестами Zephyr Scale и ее API, фреймворка Spring Boot, языка программирования Java и сервиса Ollama.
